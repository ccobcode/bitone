# 安全设计

## 1. 原则

1. **私钥不出冷钱包**:助记词,BIP39 密码,私钥,PIN 只存在于冷钱包,不会出现在任何二维码里.
2. **冷钱包不信任网页端**:签名前,冷钱包从原始交易里独立解析所有字段,并从派生路径重新算出地址比对,不采信网页端或网关给的任何描述.
3. **网页端不信任网关**:网关的数据只用来构建交易,扫回的签名要和构建记录比对后才广播.冷钱包能核对收款方,金额和手续费,核对不了余额,UTXO 是否存在和确认数,这部分是残余风险,见第 7 节.
4. **网关少知道**:不鉴权,不存储,只收到地址.它仍能看出同一次请求里的地址可能属于同一个人,见第 5 节.
5. **气隙**:冷钱包与任何设备之间都只有二维码.

## 2. 冷钱包

### 2.1 运行前提

气隙靠硬件环境成立,以下是前提,不是建议:

- **专用手机**:恢复出厂设置,不登录账号,只安装 BitOne.在日常手机上气隙不成立.
- **系统版本**:最低 Android 12.隐藏悬浮窗等防护从这个版本开始可用.
- **安装顺序**:先装应用,再断网,再建钱包.

### 2.2 离线环境自检

启动时和签名前都执行.02 的 A1 与这张表保持一致.任一项锁定时,创建,解锁和签名都不可用.

| 检查项                           | 不通过时                                                    |
| -------------------------------- | ----------------------------------------------------------- |
| 飞行模式已开,Wi-Fi,蓝牙,NFC 已关 | 锁定签名                                                    |
| 未 Root,Bootloader 已锁定        | 锁定签名                                                    |
| 调试模式已关,USB 未连接数据      | 锁定签名                                                    |
| 硬件密钥库                       | StrongBox 通过.只有 TEE 时显示警告.两者都没有时拒绝创建钱包 |
| 系统屏幕锁已设置                 | 拒绝创建钱包                                                |
| 没有第三方无障碍服务             | 锁定助记词页和签名                                          |
| 没有被授权的悬浮窗应用           | 显示警告                                                    |

应用不申请 `INTERNET` 权限,构建时检查最终清单,任何依赖带进来都会让构建失败.需要的权限是 `CAMERA`(扫码是唯一的输入方式)和自检用的只读权限,这些权限都不能收发数据.

### 2.3 密钥保管

- **随机源**:种子由操作系统的密码学随机源生成(Rust 的 `getrandom`).
- **PIN 和硬件绑定**:解密密钥由 PIN 和硬件结果一起派生(Argon2id).硬件结果是 Keystore 里不可导出的 HMAC 密钥对 PIN 算出的,优先放在 StrongBox,没有时用 TEE.每猜一次 PIN 都要手机硬件算一次,所以密文拿走后无法离线试 PIN.
- **硬件密钥的使用条件**:每次使用都要过系统屏幕锁或指纹,没有时间窗,由硬件强制.一次确认只能算一个 PIN.Android 15 起同时要求设备处于解锁状态.
- **用完清除**:签名时解密到内存,用完立即清除.
- **链上私钥不进硬件**:链上私钥要从种子派生,硬件密钥库保管不了这种结构,所以硬件只参与解密密钥的派生.
- **每次签名都输 PIN**:PIN 是解密材料,指纹无法替代,所以不提供指纹签名.
- **错误次数**:第 5 次起递增延时,从 30 秒到 5 分钟,第 10 次抹除钱包数据.计数由应用保存,Root 后可以重置,这时限制猜测速度的是每次都要过系统屏幕锁.
- **弱 PIN**:设置时拒绝最多两种数字的组合和逐位递增递减的序列,比如 `111111`,`121212`,`123456`.
- **必须输 PIN 的操作**:签名,导出观察钱包,查看助记词,修改 PIN,抹除钱包,更新内置清单.这些操作前都要先自检.忘记 PIN 时,连续输错 10 次会抹除钱包,再用助记词恢复.
- **不需要 PIN 的操作**:查看账户地址,显示收款码,扫码和核对.这些只用到公钥,而且系统屏幕锁是运行前提.
- **抹除的前提**:助记词验证通过后才能进入首页,所以抹除只会发生在已验证备份的钱包上.
- **指纹变更**:硬件密钥不失效,新指纹能过系统确认,但仍要 PIN.指纹被更换或关闭后,手机屏幕锁不再能证明是本人,错误次数只限时:第 6 次起等 1,5,15,60 分钟,之后每次 60 分钟.这期间不抹除,设置页也不显示抹除.输对 PIN 后恢复.
- **修改屏幕锁**:硬件密钥不失效,之后用新密码确认.应用发现不了这个变更,行为不变.
- **屏幕锁被移除或被强制重置**:硬件密钥永久失效,重新设置屏幕锁也救不回.此时钱包进入"需恢复"状态,只能用助记词恢复,A1 要提前说明.
- **不进系统备份**:关闭 `allowBackup`,不使用云备份和设备迁移.

### 2.4 BIP39 密码

- 可选.不写入设备.
- 启用后,导出观察钱包和签名时都要输入,用完清除.
- 这类钱包的公钥只放内存,应用退到后台时清除.
- 输错不会报错,只会得到另一个钱包.请求里的指纹对不上时,冷钱包提示检查密码.
- 冷钱包只有一个种子,不提供钱包切换.不同的 BIP39 密码对应不同的主密钥指纹.

### 2.5 屏幕与输入

- 全部页面都开启 `FLAG_SECURE`,包括 PIN 页.
- 助记词,BIP39 密码,PIN 都用应用内置键盘,不走系统输入法.
- 隐藏其他应用的悬浮窗(`HIDE_OVERLAY_WINDOWS`),敏感按钮过滤被遮挡时的点击.
- `FLAG_SECURE` 挡不住无障碍服务,所以由 2.2 的自检拦截.

### 2.6 派生路径校验

- 只接受 [系统设计 §5](03-system.md#5-网络与派生) 白名单里的路径,其余直接拒绝.
- 路径决定链和网络.主网路径配测试网声明,或 Bitcoin 路径配 EVM 请求,都直接拒绝.
- 付款地址和找零地址都从路径重新派生,再和请求比对.
- Bitcoin 找零索引上限 100000,超出时拒绝.超过本机已签过的最高索引加 20 时,按高风险处理,防止资金被放到用户找不到的位置.最高索引按主网和测试网分开记,只增不减.导入钱包后这个值从 0 开始,第一笔可能误报高风险.
- 主密钥指纹只用来判断是否同一个钱包,4 字节可以被暴力碰撞,不作为安全依据.

### 2.7 交易风险识别

#### 判定规则

1. 先把一笔交易拆成全部动作:EVM 的调用,Solana 的每条指令,Bitcoin 的每个输出.
2. 类别取全部动作里风险最高的一个.优先级从高到低:禁止,权限变更,授权,无法识别,已识别调用,普通转账.
3. 普通转账用白名单判定.原生币直转,或内置清单里的代币合约的 transfer,才算普通转账.其余合约即使方法名是 transfer,也归为无法识别,金额显示原始整数,不显示符号.
4. 描述文件不能降级.ERC-7730 只决定怎么展示,approve 和 multicall 仍按解码出的内部动作定类别,内部看不全的按无法识别处理.

#### 类别

| 类别       | 识别范围                                                                                        | 展示                                                 | 确认方式           |
| ---------- | ----------------------------------------------------------------------------------------------- | ---------------------------------------------------- | ------------------ |
| 禁止       | 见下一节                                                                                        | AS:说明原因,只能退出                                 | 不可签名           |
| 权限变更   | TRON AccountPermissionUpdate,Solana SetAuthority,Assign,AuthorizeNonceAccount,EIP-7702 账户委托 | A6d:红色横幅,当前控制方和新控制方                    | 长按 3 秒,再输 PIN |
| 授权       | approve,increaseAllowance,setApprovalForAll,Permit,Permit2,TRC-20 approve,Solana Approve        | A6b:红色横幅,被授权方完整地址,额度(无限额度单独标出) | 长按 3 秒,再输 PIN |
| 无法识别   | 清单外的合约,未知方法,未知指令,无法离线解析的 Solana 地址查找表                                 | A6c:黄色横幅,原始数据默认展开                        | 长按 3 秒,再输 PIN |
| 已识别调用 | 有 ERC-7730 描述,且内部动作都不高于本类,内置的 Solana nonce 账户创建                            | A6:按描述渲染成可读字段                              | 点按,再输 PIN      |
| 普通转账   | 见判定规则第 3 条                                                                               | A6:金额和收款地址为主,绿色"普通转账"                 | 点按,再输 PIN      |

网页端只构建转账,所以 A6b,A6c,A6d 这几页没有来自 BitOne 自身的合法入口.这几页都要说明"BitOne 网页端不会发起这类交易",帮助用户识别网页端被入侵或被钓鱼的情况.

#### 禁止

- 没有 Chain ID 的旧式 EVM 交易,这类签名可以在多条 EVM 链之间重放.
- `chain_id` 为 0 的 EIP-7702 授权,它对所有链生效.
- `eth_sign` 和其他裸哈希签名.
- `personal_sign`,Solana 消息签名,以及 Permit,Permit2 之外的 EIP-712 消息.类型按 EIP-2612 和 Permit2 的规范逐字比对,同名但字段不同的消息也禁止,比如 DAI 的 Permit.
- 域里 `chainId` 与当前网络不符,或域的类型不含 `chainId` 和 `verifyingContract` 的 EIP-712 消息.
- 带有未参与哈希字段的 EIP-712 消息.
- 路径不在白名单,路径与网络冲突,地址与路径不符,Bitcoin 缺少必需的前序交易.

#### 无法识别时的展示

| 链     | 展示内容                                                                                           |
| ------ | -------------------------------------------------------------------------------------------------- |
| EVM    | 目标合约,方法选择器,附带金额,数据长度.数据按 32 字节分行,标出疑似地址和大额数值                    |
| TRON   | 合约类型,发起方,目标,全部字段的原始值                                                              |
| Solana | 每条指令的程序 ID,账户列表(标出签名者和可写账户),数据长度和十六进制.查找表里解析不了的账户单独计数 |

所有链都显示付款账户和交易类型.

#### Bitcoin 的额外检查

- **输入金额**:所有输入都必须带完整前序交易,冷钱包重算 txid 后取金额,否则拒绝签名.SegWit 签名只承诺自身输入的金额,骗用户签两次可以诱导超额手续费(CVE-2020-14199).只有全部输入都是 Taproot 签名且不带 `ANYONECANPAY` 时才不需要,这时签名承诺全部输入金额.
- **混合交易不例外**:SegWit 和 Taproot 混合时,Taproot 输入也要带前序交易.否则攻击者可以把 SegWit 币声明成 Taproot 输入并压低金额,分两轮骗取签名,这个攻击已在 regtest 上复现.
- **sighash**:SegWit 只允许 `ALL`,Taproot 允许 `DEFAULT` 和 `ALL`.其他合法值按高风险处理(A6e),非法值和没有对应输出的 `SINGLE` 直接拒绝.
- **找零**:路径和地址按 2.6 校验.Taproot 找零的输出密钥必须等于无脚本树的 BIP86 公钥,防止藏脚本路径.
- 以上任何一项触发高风险时进入 A6e,长按 3 秒确认.

#### 手续费告警

冷钱包用自己算出的手续费和内置阈值比较,超过时进入高风险样式.

| 链              | 阈值                                   |
| --------------- | -------------------------------------- |
| Bitcoin         | 手续费超过发送额的 5%,或超过 0.001 BTC |
| Ethereum        | Gas Limit × 最高单价超过 0.05 ETH      |
| BNB Smart Chain | 超过 0.02 BNB                          |
| Polygon         | 超过 20 POL                            |
| TRON            | `fee_limit` 超过 200 TRX               |
| Solana          | 基础费加优先费超过 0.01 SOL            |

#### 每条链显示的字段

| 字段     | Bitcoin               | EVM                           | TRON                     | Solana                  |
| -------- | --------------------- | ----------------------------- | ------------------------ | ----------------------- |
| 网络     | 网络名                | 网络名和 Chain ID             | 网络名                   | 网络名                  |
| 付款账户 | 输入的账户和路径      | 地址和路径                    | 地址和路径               | 手续费支付者,全部签名者 |
| 交易序号 | 无                    | Nonce                         | 过期时间                 | nonce 账户              |
| 交易类型 | 地址类型              | 0x02 等类型字节               | 系统合约类型             | 消息版本,指令数         |
| 调用     | 无                    | 方法,合约,是否在内置清单      | 方法,合约,是否在内置清单 | 全部指令                |
| 手续费   | 实际手续费和费率      | Gas Limit,最高单价,手续费上限 | `fee_limit`              | 基础费,优先费           |
| 其他     | 全部输出,找零,sighash |                               |                          |                         |

所有链的原始数据都可展开.

#### 测试网

- 冷钱包没有测试网模式,也不用"主网""测试网"这两个词.签名本身不含网络信息,由冷钱包声明网络只会误导.页面只显示这笔交易的网络名,比如 Sepolia.
- 网络由派生路径判定,不看请求里的声明.Bitcoin,TRON,Solana 的测试链用 coin type `1'`,与主网私钥不同,所以这些链上的测试签名不可能花主网资金.这是路径层面的隔离,用户看不到.
- EVM 的测试链与主网同一把私钥,靠签名内的 Chain ID 隔离,所以旧式交易被禁止.

### 2.8 图标和代币信息不是信任依据

骗子代币常常盗用知名代币的图标和名称.所以:

- 图标,符号和小数位都只按"链加合约地址"从内置清单里取.
- 查不到就显示通用的问号图标,标"不在内置清单",金额显示原始整数.
- 不按代币名称或符号匹配图标.
- 网页端按清单条目合并同一资产的持仓.清单外的代币永远不合并,不计入总资产,不能转账.

### 2.9 内置清单更新

新代币如果都被标成未知,用户会习惯性长按.所以清单可以离线更新:

- 厂商发布签名的清单包,网页端显示二维码,冷钱包扫码导入.
- 冷钱包用内置公钥验签,版本号只增不减.清单包和 APK 用同一把 P-256 密钥签名,私钥加密保管,不进仓库.
- 清单包只更新代币和函数清单,不改任何校验规则.
- 签名通过的清单整体覆盖内置清单,包括原生币的符号和小数位.

### 2.10 安装与升级

被篡改的版本可以通过签名随机数泄露种子,二维码层看不出来.

- 发布 APK 哈希和签名证书指纹.构建的可复现范围见[验证状态](07-verification.md).
- 设置页显示版本和签名证书指纹,方便断网前核对.
- 升级要先确认助记词在手.升级包通过一次性的离线介质传入,Android 只允许同签名的版本覆盖安装.
- 签名使用确定性随机数:ECDSA 用 RFC 6979,Schnorr 的辅助随机数置零.这样第三方可以用同一请求复算签名,发现被篡改的版本.

## 3. 网页端

网页端能被入侵,所以它的目标是减少攻击面,资金防线仍在冷钱包.

- **托管**:静态资源全部同源,含图标和字体,不加载第三方脚本.文件名带内容哈希,发布时公布构建哈希.
- **CSP**:`default-src 'none'`,脚本,样式,字体,图片和 Web App 清单只允许同源,`connect-src` 只允许同源,禁止内联脚本,禁止被嵌入页面.核心库是 WASM,所以 `script-src` 要加 `'wasm-unsafe-eval'`,它只允许编译 WASM,不允许 `eval`.
- **网关地址固定**:官方站只连官方网关.自部署时网页端和网关同域部署,所以严格的 `connect-src` 不用放宽,也不会遇到 HTTPS 页面连不上局域网网关的问题.
- **链上文本不可信**:代币名,备注等来自链上的内容只当纯文本渲染,去掉控制字符和不可见字符,限制长度.
- **存储**:IndexedDB 不加密,与浏览器同等保护.其中有 Bitcoin 账户的扩展公钥和全部地址.恶意扩展可以读走,这是隐私泄露,不能动用资金.建议用独立的浏览器配置.
- **备份**:导出文件用口令加密,见 [系统设计 §3](03-system.md#3-浏览器存储).备份不含网关地址.导入的联系人标为待确认,要用户逐个确认后才用于转账.

## 4. 收款与配对核验

威胁表不只有付款被篡改.被入侵的网页端可以展示攻击者的收款地址,恶意备份也能植入攻击者的公钥.

- **收款**:W7 显示地址.收款二维码是纯地址,给付款方扫.核对时显示路径,核对二维码带路径,用户在冷钱包扫码(A9)核对.冷钱包从路径重新派生,显示"属于本钱包"或"不属于".未核对的地址在 W7 标为未核对.
- **配对**:W2 保存后直接打开第一个收款地址的核对,再开始收款.
- **备份恢复**:恢复出来的账户全部标为未核对.
- **地址投毒**:地址簿和转账页不以历史记录作为可信依据.交易详情不提供转给对方地址和存入地址簿的入口,这个浏览器发起的失败交易可以重新发起.不显示"转账过 N 次",首次转账的地址单独标出,与已有地址首尾相同但中间不同的地址要警告.零金额转入不进地址建议.
- 网页端的"已核对"标记也可能被伪造,所以唯一的依据是冷钱包屏幕.

## 5. 网关

- 不存储,不鉴权.限制单次请求的地址数量和单连接的订阅数量.
- 不记录地址与 IP 的对应关系.所有带地址和交易哈希的查询都用 POST,避免进入负载均衡和 CDN 的访问日志.
- 网关不决定 Chain ID 和区块浏览器链接,这些内置在网页端,见 [系统设计 §4.2](03-system.md#42-http-接口).
- 限流用来控制成本,不用来防攻击.按 IP 限流时放宽阈值,避免误伤运营商 NAT 下的用户.CORS 只限制浏览器里的来源,不能防刷.只有配置的受信任代理才能用 `X-Forwarded-For` 声明来源,单 IP 的 WebSocket 连接数有上限.
- 局限:网关和上游节点服务商都能看到查询的地址,也能看出同一次请求里的地址可能属于同一个人.介意的用户可以自己部署,并连接自己的节点.

## 6. 威胁与对策

| 威胁                                   | 对策                                                          |
| -------------------------------------- | ------------------------------------------------------------- |
| 网页端或网关被入侵,篡改收款地址或金额  | 冷钱包独立解码,展示完整地址,用户分段核对                      |
| 网页端展示攻击者的收款地址             | 收款地址在冷钱包核对(A9)                                      |
| 恶意备份植入攻击者公钥                 | 恢复的账户标为未核对,要在冷钱包核对                           |
| 恶意网站诱导签授权或权限变更           | 冷钱包识别,红色横幅,长按确认                                  |
| 伪装成普通调用的恶意合约               | 普通转账用白名单判定,其余按无法识别处理                       |
| 把授权藏在转账后面                     | 类别取全部动作的最高风险                                      |
| 找零被放到极大的派生索引               | 路径白名单和索引上限                                          |
| 网关谎报 UTXO 金额,诱导多付手续费      | 除全 Taproot 交易外,输入都必须带前序交易,冷钱包自己算手续费   |
| 仿冒代币                               | 图标,名称,小数位只信内置清单                                  |
| 把主网交易标成测试网                   | 网络由派生路径判定.TRON,Solana 测试网用不同私钥               |
| 跨链重放                               | 禁止旧式 EVM 交易和 `chain_id` 为 0 的授权                    |
| 地址投毒和地址簿污染                   | 见第 4 节                                                     |
| 恶意网关提供错误的 Chain ID 或钓鱼链接 | 这些内容内置在网页端                                          |
| 跨站脚本和恶意依赖                     | CSP,同源托管,链上文本不可信                                   |
| 恶意浏览器扩展                         | 只能读到公钥和地址.冷钱包核对是资金防线                       |
| 恶意二维码数据                         | 解析前限制总字节,帧数和嵌套深度                               |
| 第三方输入法,无障碍服务,悬浮窗         | 内置键盘,自检拦截,隐藏悬浮窗                                  |
| 被篡改的安装包                         | 发布哈希和证书指纹,确定性签名                                 |
| 冷钱包手机丢失                         | 种子需要 PIN 和硬件密钥才能解开,错误 10 次抹除,可用助记词恢复 |
| 浏览器数据被清除                       | 冷钱包重新扫码恢复,地址簿用加密备份恢复                       |
| 签名结果被替换                         | 网页端用公钥验证签名,并比对构建记录                           |
| 广播结果不明时重复付款                 | 重建必须复用同一 nonce 或同一组 UTXO                          |
| 网关被刷爆                             | 限流,请求上限,上游节点自动切换                                |

## 7. 残余风险

设计没有消除这些风险,用户文案里不能宣称已解决:

| 风险                 | 说明                                                                                                                                                          |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 余额和入账可以被伪造 | 恶意网关能伪造余额,入账和确认数,冷钱包无法验证.大额收款要在其他来源核对                                                                                       |
| 取消不等于作废       | 已签名的交易在作废之前一直有效,见 [系统设计 §9](03-system.md#9-有效期与最终性)                                                                                |
| 手机被 Root          | 恶意程序能截获 PIN,或读取显示助记词时内存里的文字.不知道屏幕锁时猜不了 PIN.知道屏幕锁时可以在本机自动尝试 6 位 PIN,速度受硬件限制.高价值用户应启用 BIP39 密码 |
| 只有 TEE 的手机      | 硬件保护弱于 StrongBox,自检时要显示                                                                                                                           |
| 没有遵守专用手机前提 | 气隙不成立,应用只能部分检测                                                                                                                                   |
| 隐私                 | 网关,节点服务商,恶意扩展都能关联用户的地址                                                                                                                    |
| 用户不看就确认       | 长按和横幅只能降低概率                                                                                                                                        |
| 发布私钥泄露         | 清单和 APK 共用一把私钥.拿到它既能发布清单,改任何资产的符号和小数位,也能签发应用更新,冷钱包发现不了,发新版也撤销不了                                          |
